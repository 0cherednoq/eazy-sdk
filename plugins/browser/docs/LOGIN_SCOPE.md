# Автологин в браузере: где живёт сессия

пересматривает шаги B7.2 и B7.3 из `LAYERS.md`. Вопросы прежней редакции (§5) закрыты;

---

## 1. Цель

Удобство должно остаться таким же, как у HTTP-клиента `eazy-sdk`. SDK сам знает, как
входить на сайт. Пользователь вызывает любой метод, а SDK сам проверяет сессию, при
необходимости входит, вызывает метод и при протухшей сессии входит заново и повторяет.
Пользователь жизненный цикл не собирает.

Границу из `LAYERS.md` §0 это не нарушает: SDK знает, **когда нужна сессия и как её
получить**, — ровно столько же, сколько HTTP-ядро. Контексты, число вкладок, прокси и
аренда по-прежнему не его забота.

---

## 2. Как это устроено в HTTP-ядре (проверено по коду)

- `session_cookie(...)` и `session_auth(...)` создают **один `SessionProvider` на объект
  `Auth`** (`eazy_sdk/auth/session_runtime.py:521`, `:660`). Внутри провайдера —
  `SessionLifecycle` (`session_runtime.py:129`).
- У `SessionLifecycle` есть свой `asyncio.Lock` (`eazy_sdk/auth/session.py:168`).
  `resolve()` работает под ним: берёт сессию из хранилища, проверяет, при необходимости
  обновляет, иначе входит заново и сохраняет результат. Если параллельно пришло N
  вызовов, войдёт только один, остальные получат готовую сессию.
- Если сервер отверг сессию, вызывается `SessionProvider.refresh_execution` →
  `SessionLifecycle.refresh_revision(revision)` (`session.py`, `refresh_revision`).
  Входит заново только тот, кто держит самую свежую ревизию. Остальные видят, что
  ревизия уже новее, и повторяют запрос без входа. Число повторов задаёт
  `ClientConfig.auth_retries`, по умолчанию 1 (`eazy_sdk/clients/config.py:37`).

Две оговорки:

- **Лок живёт внутри процесса и привязан к объекту `Auth`.** Если создать два `Auth` для
  одного аккаунта, у каждого будет свой лок. Между процессами лока нет: дубли там
  отсекают только ревизии в хранилище, и то лишь для повторного входа (первый вход в
  двух процессах может пройти дважды).
- **Лок стоит на уровне аккаунта, а не соединения.** Сессия путешествует с каждым
  запросом в заголовке, соединение о ней ничего не хранит. Поэтому одного объекта на
  аккаунт достаточно.

## 3. Почему браузер нельзя скопировать один в один

В браузере сессия лежит **в контексте**, в его куках и localStorage. Поэтому у объекта,
который отвечает за сессию, естественная единица владения — контекст, а не аккаунт и не
вкладка:

- **Вкладка — слишком мелко.** Так устроено сейчас: `_SignIn` живёт в
  `AsyncBrowserClient` (`client.py:118-146`), клиент привязан к одной вкладке. Пять
  вкладок аккаунта — это пять локов, пять жизненных циклов, пять входов в общий
  контекст и пять `import_state` (ревью, п. 1).
- **Аккаунт — слишком крупно.** Один объект на аккаунт вынужден помнить, в какой из
  контекстов аккаунта какая ревизия уже положена, и держать лок на каждый контекст. Это
  уже решение «что делать, когда страниц несколько», которое `LAYERS.md` §0 запрещает
  одной фразой. Прежняя редакция этого документа предлагала именно такую форму
  (`WeakKeyDictionary[контекст, ревизия]`); она снята.

Ревью сделало вывод «уберите вход из SDK». Правильнее другое: сохранить автологин и
разнести три вещи с разным временем жизни по разным объектам.

| Что | Живёт | Владелец |
|---|---|---|
| Знание сайта: как войти, какая кука обязательна, какие отказы значат «протухла» | вечно, одно на SDK | плагин, `BrowserLogin` |
| Жизненный цикл сессии: хранилище, ревизия, single-flight, повторный вход | столько, сколько контекст | тот, кто владеет контекстом: `BrowserSession` без пула, пул — с пулом |
| Клиент: выполнить операцию на странице | столько, сколько вкладка | плагин, `AsyncBrowserClient` |

## 4. Решение

### 4.1. `BrowserLogin` — только знание сайта

```python
MAIL_LOGIN = BrowserLogin(          # одно на SDK, общее для всех аккаунтов
    service=MailLogin(),            # async acquire(credentials, context) -> BrowserState
    cookies=("sid",),               # без живой sid сессия не сессия
    expired=(SessionExpiredError,), # отказы, после которых входят заново
)
```

Уходят `credentials`, `store`, `identity`, `retries`, `key`, `lifecycle()`. Остаются
`service`, `cookies`, `expired`, `leeway`, `clock` и чистые методы `validate(state)`,
`is_expired(error)`, `sign_in(client, credentials)`, `refresh(client, credentials, state)` —
как в `LAYERS.md` §2.1. Ни блокировок, ни хранилища, ни повторов.

### 4.2. Клиент зависит от протокола, а не от реализации

Клиенту нужны ровно два действия: «сессия в браузере есть?» и «сервер отверг ревизию,
что дальше?».

```python
class SessionSource[TRevision](Protocol):
    async def ensure(self, client: AsyncBrowserClient) -> TRevision: ...
    async def renew(self, client: AsyncBrowserClient, rejected: TRevision) -> TRevision | None: ...

AsyncBrowserClient(driver, base_url=BASE, session=source)   # вместо login=
```

Протокол живёт в `client.py`, рядом с тем, кто его принимает: так клиент не тянет
`session.py`, а с ним жизненный цикл ядра (граф импортов — `LAYERS.md` B7.6). Ревизия
для клиента непрозрачна: он её только держит и отдаёт обратно в `renew`, поэтому
`BrowserSession` работает с `SessionRevision` ядра, а источник пула — с поколением
контекста, и `client.py` не импортирует `eazy_sdk.auth.session` даже под `TYPE_CHECKING`.

Источник получает клиент, а не драйвер: для входа нужен клиент без сессии на той же
странице, с `base_url` и `config` вызывающего. Его отдаёт
`AsyncBrowserClient.without_session()`.

Цикл клиента: `ensure(self)` → операция → отказ, для которого `is_expired` истинно →
`renew(self, rejected)` → ревизия → повтор. Число повторов — `BrowserClientConfig.auth_retries`
(по умолчанию 1, как у ядра). `renew` вернул `None` — повторов нет, клиент заново бросает
исходный отказ из `expired`: наружу уходит отказ сайта, а не исключение источника.
`session=None` — клиент без входа, как и сейчас у сервиса входа (`BrowserLoginContext`).

Клиент не знает ни про хранилище, ни про контексты, ни про локи. `_SignIn`,
`_run_signed_in`, `sign_in()` и `_login_context` удаляются.

### 4.3. Без пула: `BrowserSession` — один объект на контекст

```python
# аналог session_cookie(...) → Auth, но единица владения — контекст, а не аккаунт
mail = MAIL_LOGIN.session(
    credentials=creds,
    store=sessions.store(account),  # по желанию; по умолчанию — в памяти
    identity="user@example.com",
)

async with (
    AsyncBrowserClient(PlaywrightDriver(page1), base_url=BASE, session=mail) as a,
    AsyncBrowserClient(PlaywrightDriver(page2), base_url=BASE, session=mail) as b,
):
    await MailPortal(a).send(...)   # пять вкладок одного контекста делят один объект и один вход
```

Устройство — прежний `_SignIn`, перенесённый из клиента в отдельный объект:

1. **`SessionLifecycle` ядра** с его собственным локом: хранилище → `validate` → иначе
   вход на странице того клиента, который первым упёрся в отсутствие сессии
   (`client.without_session()` → `BrowserLoginContext`). `acquire` и `refresh` жизненного
   цикла — тонкие адаптеры над `login.sign_in` и `login.refresh`: путь входа один,
   проверка результата только в `BrowserLogin`. N вкладок, одновременно пришедших в
   `ensure`, дают один вход. `context_factory` у жизненного цикла один на объект, а
   страница входа у каждого вызова своя, поэтому `ensure`/`renew` кладут клиент в
   `ContextVar` на время `resolve`/`refresh_revision`, а фабрика читает его оттуда; под
   локом входит один вызов, значение однозначно. Адаптеры `acquire`/`refresh` ставят
   `applied_by_login_here` для п. 3 только после успешного результата `sign_in`/`refresh`:
   фабрика вызывается до входа, и упавший вход оставил бы признак при старом `applied`.
   `session(...)` требует непустой `cookies` и падает
   `BrowserDeclarationError` при сборке: без объявленной куки `validate` проверяет лишь
   непустоту состояния, а кука аналитики в живом контексте есть почти всегда, и
   сохранённая сессия никогда бы не легла.
2. **Поля `applied` и `applied_by_login_here`** плюс **свой лок на весь шаг** «посмотреть в
   контекст → разрешить → положить куки → `applied`», как `_SignIn.lock` сегодня: без него
   параллельные вкладки сделали бы несколько записей. Первый `ensure` смотрит в контекст
   **раньше**, чем в хранилище: если `login.validate(export_state())` истинно, а в
   хранилище годной сессии нет, состояние контекста принимается через
   `lifecycle.adopt(...)` (ядро проверяет и сохраняет под тем же локом, ревизия новая) —
   без входа и без записи. Иначе второй контекст со `storage_state` из другого хранилища
   или с `store=None` вошёл бы заново поверх годной сессии. Быстрые пути, как у `_SignIn`:
   `ensure` при непустом `applied` отдаёт его, не читая хранилище; `renew(rejected)` при
   `applied > rejected` отдаёт `applied`, не трогая ни хранилище, ни контекст — сосед со
   старой ревизией повторяет операцию сразу. Хранилище читается при первом `ensure` и в
   `renew` с `rejected == applied`. Никакой карты контекстов: объект и есть контекст. Перед первым `ensure` — `require_state(driver)`:
   драйвер без `session_state` отсекается до входа; клиент этого не проверяет, потому
   что знает только протокол, а источнику пула `session_state` может не понадобиться.
3. **В контекст кладутся только куки** (`StateAware.add_cookies`), и только когда их там
   нет. При первом `ensure` — только если контекст не прошёл `validate` в п. 2 и сессия
   пришла из `resolve()`: контекст со `storage_state` от слоя выше и контекст, где сайт
   сам ротировал куку, записи не получают (иначе свежую куку затёрла бы старая из
   хранилища). После `renew`, когда
   хранилище читалось, — если новая ревизия пришла из хранилища, а не из входа в этот
   контекст: вход здесь уже положил куки сам, а ревизию из хранилища добыл соседний
   объект, и в этом контексте её ещё нет. Признак считается по объекту, не по вызову:
   `applied_by_login_here` ставят адаптеры `acquire`/`refresh` после успешного входа, а
   сбрасывает `renew`, взявший ревизию из хранилища. Сравнение
   значений кук не делается: по значениям ротацию от протухания не отличить. Годную на
   вид, но мёртвую сессию отсеет сервер: отказ → `renew` → вход.
4. **`renew(rejected)`** при `rejected == applied` → `refresh_revision(rejected)`: входит
   заново только держатель самой свежей ревизии; соседние вкладки с тем же отказом ждут
   лок, видят `applied > rejected` и выходят по быстрому пути без входа и без записи.
5. **Защита, а не оркестрация:** объект запоминает `StateAware.context_key()` первого
   клиента (непрозрачный ключ контекста, для playwright — `page.context`, сравнение
   только на равенство) и бросает `BrowserSessionError`, если тот же объект принёс
   клиент с другим ключом. Это проверка инварианта «один объект на контекст», решений
   «когда контекстов несколько» здесь нет.
6. **`await mail.state(client)`** — разрешить сессию без операции: для
   `browser_cookie_auth` и для `to_storage_state` при создании следующего контекста.
   Страница нужна: без неё хранилище не разрешить и входить негде. Контексту «до первой
   вкладки» `storage_state` даёт хранилище напрямую (`BrowserSessions.load(account)`), а
   если там пусто — первый контекст открывается без `storage_state`; второй контекст с
   полученным состоянием входить не будет, п. 2 примет его через `adopt`. `state()` без
   клиента не делается: второй путь разрешения сессии.

Два контекста одного аккаунта — два `BrowserSession` **с общим `store`**, это
обязанность вызывающего: `store=None` даёт каждому объекту своё хранилище в памяти, и
после повторного входа два контекста не согласуют ревизии. Согласует их только хранилище,
ровно как два `Auth` в HTTP (§2, первая оговорка).

### 4.4. С пулом: источник сессии — пул, вход внутри контекста запрещён

Пул (`browser-pool`) уже владеет всем жизненным циклом контекста: создаёт контекст с
`storage_state` из своего `StateStore`, в `SessionFlow.open` проверяет и при
необходимости входит на временной вкладке, сохраняет состояние сразу после `open`,
а на `ErrorKind.session` закрывает контекст и открывает новый. Второй жизненный цикл
внутри контекста ему только мешал бы: повторный вход `BrowserSession` шёл бы
одновременно с retire контекста пулом.

Поэтому при работе через пул клиент получает источник, который **ничего не делает**:
`ensure` возвращает ревизию контекста, `renew` возвращает `None`, и клиент бросает
исходный отказ сайта. Отказ доходит до классификации пула, становится
`ErrorKind.session`, контекст уходит, следующий `open` входит заново. Повторный вход никогда не меняет куки под соседними вкладками, потому
что идёт в новом контексте.

```python
async with pool.page(any_of=identities) as lease:
    client = await lease.attachment("mail", lambda page: mail_client(page))   # session=PoolSession(lease)
    await MailPortal(client).send(...)
```

Адаптер `BrowserLogin` → `SessionFlow` и `PoolSession` живут на стороне eazy как
необязательный модуль `integrations/pool` (`browser-pool` в план интеграцию не
включает, см. `browser_pool/docs/EAZY_SDK_REVIEW.md`). От плагина ему нужны только чистые
функции: `validate`, `service.acquire(credentials, client)`, `is_expired` и конвертеры
`BrowserState` ↔ `storage_state`. Этот модуль — вне B7; здесь фиксируется только, что
форма §4.1–4.2 его допускает без изменений плагина.

- **B7.7** — пример «слой выше в коде пользователя» сокращается: без пула это

  не делается жизненный цикл **на уровне аккаунта или страницы**; жизненный цикл

- **Определение готовности, п. 3** — «без общего объекта плагина между ними»

## 5. Решения

Нумерация та же, что у вопросов прежней редакции.

1. **Как класть сессию в уже открытый контекст.** Только куки, через `add_cookies`, из
   `BrowserSession.ensure`. Init-скрипт для localStorage удаляется целиком, включая
   вариант «писать ключ, только если его нет»: он лечит симптом и оставляет в плагине
   запись, которую нельзя отменить. Если сайту нужен localStorage, контекст создаётся с
   `storage_state` из хранилища (`BrowserSessions.load(account)`) или из
   `await mail.state(client)` после первого входа — это забота того, кто
   создаёт контекст, и в обоих режимах (§4.3, §4.4) это уже так.
2. **Повторный вход при работающих соседних вкладках.** Без пула — принимается и
   документируется: сессия общая на контекст, соседи получат тот же отказ, дождутся лока
   и повторят с новой ревизией. Режим «вход в отдельной вкладке» не делается. С пулом
   вопроса нет: повторный вход идёт в новом контексте.
3. **Где входить.** На странице первого клиента, упёршегося в отсутствие сессии; после
   входа операция начинается с объявленного перехода. Фабрика страниц для входа не
   даётся: это оркестрация. У пула вход идёт на временной вкладке из `ctx.new_page()`.
4. **Кто владеет входом при пуле.** Пул, целиком (прежний вариант (б)). Клиент получает
   `PoolSession`, который не входит и не повторяет. Вариант «пул зовёт
   `BrowserSession.ensure` в `open`» отвергнут: два жизненных цикла на контекст.
5. **Несколько процессов на один аккаунт.** Как в HTTP: лок в процессе, между процессами
   только ревизии хранилища; первый вход может пройти дважды. Межпроцессный лок — задача
   `eazy_sdk_accounts`, `CORE_DEBT.md`. У пула сверх того оптимистичная версия записи в
   `StateStore`.
6. **Один `BrowserSession` на контекст — обязанность пользователя.** Документируется, не
   кешируется. Нарушение в одну сторону (два контекста, один объект) ловит защита из
   §4.3 п. 5; в другую (один контекст, два объекта) — не ловится, как два `Auth` в HTTP.
7. **Мост в HTTP.** `await mail.state(client)` вместо `client.sign_in()`. HTTP-`Auth` после
   повторного входа по-прежнему статичен (`CORE_DEBT.md` п. 7); до починки ядра этого
   достаточно.
