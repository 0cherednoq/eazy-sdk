# Условия OpenAPI 3.1 и теги ответа

Тип документа: исследование + предложение синтаксиса. Написан 2026-09-09 по вопросу владельца:
«в OpenAPI 3.1 есть условия, ими было бы удобно генерировать код; один из юз-кейсов — описание
успешного и неуспешного ответа; сейчас условия выражаются прямо в модели, возможно это не лучшее
решение».

Замеры воспроизводимы: скрипты лежат в `experiments/openapi_conditions/`, перечень — в §11.

---

## 0. Короткий ответ

1. Условия в 3.1 действительно есть — весь словарь JSON Schema 2020-12, включая
   `if`/`then`/`else`, `dependentSchemas`, `dependentRequired`, `const`. **В реальных спеках их
   ноль**: 0 вхождений на ~65 МБ и ~6300 операций в 16 спеках, включая три спеки 3.1 (§1).
2. Ответы в реальном мире различают четырьмя вещами: **статус** (плюс диапазоны `4XX` и
   `default`), **media type**, **`oneOf`/`anyOf`** (иногда с `discriminator`) и — для нашего
   юз-кейса главное — **константу на поле** (`const` или одноэлементный `enum`).
3. Именно константа на поле описывает «успех/неуспех внутри 200»: Slack — `ok: enum[true]` против
   `ok: enum[false]`, Stripe — `deleted: enum[true]` в `deleted_customer`, Cloudflare — конверт
   `{success, result, errors, messages}` (§1.2).
4. Поэтому предлагаемый синтаксис — **не язык условий, а тег-поле в модели плюс маркер полезной
   нагрузки**, оба через `Annotated`: они выводятся из схемы механически, обратно в схему тоже
   выводятся, проверяются mypy и не требуют ни одной лямбды.
5. Диагноз к фразе «условия в модели — возможно, не лучшее решение» уточняется: **условие в модели
   — правильно, вердикт в модели — неправильно**. `Envelope.succeeds` отвечает «это успех», то есть
   выносит вердикт, а вердикт принадлежит объявлению операции. Тег отвечает «в этом теле
   `success == false`» — это свойство схемы, и ему место в модели, ровно как `const` живёт в схеме
   OpenAPI. После замены вердикт возвращается туда, где он уже есть: в то, в какой словарь
   (`success=` или `errors=`) положена модель.

### 1.2. Как в реальности описывают «успех и неуспех на одном статусе»

Slack, `admin.conversations.create` (и все 174 метода одинаково):

```jsonc
"200":     { "schema": { "properties": { "ok": { "$ref": "#/definitions/defs_ok_true" },  "channel_id": {…} }, "required": ["ok"] } }
"default": { "schema": { "properties": { "ok": { "$ref": "#/definitions/defs_ok_false" }, "error": { "enum": ["name_taken", "invalid_auth", …] } }, "required": ["ok", "error"] } }

"defs_ok_true":  { "type": "boolean", "enum": [true],  "title": "default success response" }
"defs_ok_false": { "type": "boolean", "enum": [false], "title": "default failure response" }
```

Stripe, `GET /v1/customers/{customer}` → 200:

```jsonc
{ "anyOf": [ { "$ref": "#/components/schemas/customer" }, { "$ref": "#/components/schemas/deleted_customer" } ] }
// deleted_customer: properties.deleted = { "type": "boolean", "enum": [true] }, required: ["deleted","id","object"]
```

Cloudflare, `GET /accounts/{id}/ai/models/search` → 200: `anyOf` из конверта
`{success, result, errors, messages}` (все четыре в `required`) и «маркетплейсного» формата `{data}`.

GitHub, `PATCH /orgs/{org}` → 422: `oneOf` из `validation-error` и `validation-error-simple` —
**у обеих одинаковый `required` и одинаковый набор полей**, различаются только типом элементов
`errors`. Честный вывод: часть союзов в реальном мире неразрешима без разбора, и любой механизм
обязан иметь определённое поведение на таком случае (у нас — `AmbiguousResponseError`).

Отдельно: вендоры выражают смысл не условиями, а расширениями — Stripe кладёт
`x-expandableFields`/`x-resourceId`, Speakeasy — `x-speakeasy-pagination` (по нему сделана фаза 52).
Расширение — принятый в отрасли способ дописать спеке то, чего в ней нет.

## 2. Что говорит спецификация

1. **`if`/`then`/`else` — аппликатор, а не выбор.** JSON Schema 2020-12 core, §10.2.2: результат
   валидации подсхемы `if` сам по себе не влияет на общий результат — он только решает, какая из
   `then`/`else` будет применена. Общее правило аппликаторов там же: они комбинируют результаты
   подсхем булевой логикой и **не вводят собственных утверждений**. То есть `if` отвечает на
   вопрос «валидно ли значение», а не «какой это случай».
2. **`oneOf` — «ровно одна подсхема валидна».** Это тоже утверждение о валидности; выбор из него
   выводится только если ветки различимы, что и делает `discriminator`.
3. **`discriminator` — подсказка, а не ключевое слово валидации** (OpenAPI 3.1.1, §4.8.25):
   `propertyName` — имя поля, несущего значение дискриминатора, `mapping` — отображение значений в
   схемы. Спека прямо не относит его к валидации; он существует ради (де)сериализации и кодогена.
4. **Responses** (§4.8.16): ключи — коды, диапазоны вида `2XX` и `default`.
5. **Schema Object — надмножество JSON Schema 2020-12** (§4.8.24), поэтому `const`, `if`,
   `dependentSchemas` формально разрешены. Разрешены — но, по §1, не используются.

Из этого следует разделение, которое стоит держать в голове при любом дизайне:

| Вопрос | Кто отвечает в OpenAPI | Кто отвечает у нас сейчас |
|---|---|---|
| **Выбор**: какой это случай | статус + media type + `oneOf`/`discriminator` | `status` + `media_type` + `when=`/`accept=`/`__envelope__.succeeds` |
| **Валидация**: корректно ли тело | схема | модель + адаптер |
| **Проекция**: что именно вернуть вызывающему | *ничего, понятия нет* | `unwrap=` (указатель до разбора), `__envelope__.payload` (после) |

Условия JSON Schema живут в колонке «валидация». Нам они нужны в колонке «выбор». Совпадают эти
колонки ровно в одном случае: когда ветки различаются **константой на поле**. Это и есть тот
подмножественный, разрешимый кусок условий, который реально пишут (§1.2).

## 3. Диагноз: тег — не вердикт

Сейчас на модели объявляется `Envelope(succeeds=…, payload=…)`, и `succeeds` инвертируется видом
кейса (I5 фазы 53): success-кейс совпадает на истине, error-кейс — на лжи.

Что здесь не так:

- **`succeeds` — вердикт.** «Этот конверт успешен» — утверждение про исход вызова, а не про форму
  данных. Контрпример измеренный, не выдуманный: Stripe `deleted_customer` со статусом 200 — для
  `GET /v1/customers/{id}` это успех (объект существует, он удалён), а для операции «дождись, пока
  клиент активен» тот же ответ — неуспех. Модель не может этого знать; знает объявление операции.
- **Два зеркальных вопроса с похожими именами.** `Envelope.succeeds` инвертируется, `accept=` — нет
  (D3/D5 фазы 53 это признают и принимают риск). Ровно одно понятие требуется в двух формулировках.
- **Лямбда непрозрачна.** Её нельзя показать в диагностике (`<lambda>`), нельзя вывести из спеки
  иначе как генерацией кода лямбды, нельзя вывести обратно в спеку, а тип результата приходится
  доставать `get_type_hints` из аннотации возврата — и если её нет, мы не знаем ничего (§3.6 фазы 53).

Что при этом правильно и должно остаться: **само условие принадлежит схеме**. `const` в OpenAPI
живёт в схеме, схема переиспользуется многими операциями — и объявление на модели даёт то же
свойство: один конверт сервиса описан один раз.

Отсюда предложение: оставить в модели **факт** («поле `success` в этом теле равно `false`»), убрать
из модели **вердикт** («значит, это ошибка»). Вердикт возвращается в объявление операции — туда, где
он уже выражен тем, в какой словарь положена модель.

## 4. Предлагаемый синтаксис

Два маркера в `Annotated`. Оба читаются нами, оба игнорируются всеми четырьмя бэкендами моделей
(измерено, §7), оба выводятся из схемы и в схему.

```python
from typing import Annotated
from eazy_sdk.response import Const, Payload
```

- `Annotated[T, Const(value)]` — **тег**: поле обязано быть равно константе. Прямой перевод
  `const` / одноэлементного `enum`.
- `Payload[T]` — **полезная нагрузка**: это поле и есть результат операции. Обычный generic-алиас
  над `Annotated`, как `Query[int]`/`Path[str]` на стороне запроса (фаза 50).

### 4.1. kad: до и после

Сейчас (после 53.3):

```python
class DocumentPageResponse(msgspec.Struct, rename={"result": "Result", "success": "Success"}):
    result: DocumentPage
    success: bool
    message: str | None = None

    __envelope__ = Envelope(succeeds=lambda r: r.success, payload=lambda r: r.result)
```

Предлагается:

```python
class DocumentPageResponse(msgspec.Struct, rename={"result": "Result", "success": "Success"}):
    success: Annotated[bool, Const(True)]
    result: Payload[DocumentPage]
    message: str | None = None


class KadFailure(msgspec.Struct, rename={"success": "Success", "message": "Message"}):
    success: Annotated[bool, Const(False)]
    message: str
```

Объявление операции не меняется — и вердикт теперь виден прямо в нём:

```python
class CaseDocumentsPage(HttpOperation[DocumentPage]):
    __http__ = Http.get(
        "/Kad/CaseDocumentsPage",
        success={200: Json(DocumentPageResponse)},
        errors={200: (Json(KadFailure), KadRequestFailed)},   # обычно — атрибут сервиса, один раз
    )
```

`KadFailure` — общая для сервиса модель, поэтому `errors` объявляется один раз на миксине сервиса
и наследуется по MRO, как `errors` уже работает сегодня.

### 4.2. Slack: то, что генератор выведет сам

```python
class PostMessageOk(msgspec.Struct):
    ok: Annotated[bool, Const(True)]
    channel: str
    ts: str


class SlackFailure(msgspec.Struct):
    ok: Annotated[bool, Const(False)]
    error: str
```

Обе модели механически получаются из `enum: [true]` / `enum: [false]`, без единой строки ручной
работы и без лямбд.

### 4.3. Правила

- **R1.** Кейс совпадает, если совпали *все* теги его модели. Несовпадение — `NoMatch`, то есть
  кейс просто не претендует на этот ответ; арбитраж продолжается другими кандидатами. Это не
  `Malformed`: тело не сломано, оно про другой случай.
- **R2.** Тег **не инвертируется** видом кейса. Он говорит только «поле равно значению», одинаково
  для `Success` и для `Error`. Вердикт даёт объявление, а не модель. Это снимает асимметрию
  `succeeds`/`accept`.
- **R3.** Ранг критерия не меняется (I3 фазы 53): у кейса либо есть критерий, либо нет. Модель с
  тегом даёт критерий — как `when=` и `accept=`.
- **R4.** `Payload` применяется только к success-кейсу (правило 53.3 сохраняется: ошибке нужен весь
  конверт — там `message` и код). Ровно одно поле в модели может нести `Payload`, иначе — ошибка
  объявления.
- **R5.** Тип результата операции читается из `Payload[T]` **статически**: `HttpOperation[T]`
  сверяется с маркером при импорте. Никакого `get_type_hints` по лямбде и никакого «лямбда без
  аннотации ничего не сообщает».
- **R6.** `Literal[...]` на поле означает то же самое и даёт тот же критерий там, где бэкенд его
  тянет. Это не второй механизм, а второе написание одного: константный тип поля и есть тег.
  Оговорка измерена (§7): `Literal[True]` на msgspec невозможен в принципе, а наши адаптеры
  dataclass и TypedDict сегодня не поддерживают `Literal` вообще. Пока это так, переносимая форма —
  `Const(...)`, и именно её пишет генератор.
- **R7.** Остаётся `when=` — решение до разбора по сырому телу (страница капчи, PDF): теги про него
  ничего не знают и знать не должны.
- **R8.** Остаётся `accept=` на кейсе — для чужой модели, которую нельзя тронуть, и для условия,
  которое не сводится к равенству (`not any(e.fatal for e in errors)`).

### 4.4. Что при этом происходит с `Envelope`

Если R1–R8 приняты, `Envelope` покрывается целиком: `succeeds` → тег, `payload` → `Payload[T]`.
Держать оба — значит держать два способа сказать одно и то же, чего проект избегает по правилу
«ни одного второго механизма». `Envelope` **не входил ни в один релиз** (все коммиты фазы 53 лежат
после тега v0.2.0a7), поэтому его удаление ничего не ломает снаружи и не требует депрекации.

Аргумент против (его надо принять сознательно): вычисляемое условие уровня сервиса — например
«успех, если `errors` пуст» — после удаления `Envelope` пишется как `accept=` на кейсе, то есть в
объявлении сервиса, а не на модели. Мне это кажется правильным (это опять вердикт, а не факт), но
это смена места объявления, и решать владельцу (D2 ниже).

## 6. Кодоген: таблица соответствий

| Конструкция в спеке | Что генерируем |
|---|---|
| `responses: {"200": …}` | `success={200: Json(Model)}` |
| `"4XX"`, `"5XX"` | `StatusRange(400, 499)` |
| `"default"` | `fallback=` |
| несколько media type на статусе | несколько кейсов с `media_type=` |
| несколько 2xx у операции | несколько success-кейсов |
| `const` / одноэлементный `enum` на поле | `Annotated[T, Const(value)]` |
| `oneOf`/`anyOf`, ветки различаются тегом | N кейсов + теги; вердикт — по статусу |
| `oneOf`/`anyOf` + `discriminator` | **tagged union как тип модели** (msgspec `tag=`/`tag_field=`, Pydantic `Field(discriminator=)`) — работает сегодня, проверено (§7.3). Это полиморфизм нагрузки, а не вердикт: один кейс, союзная модель |
| `oneOf` без различающего признака (GitHub `validation-error`) | союзный тип + запись в отчёт анализа; вердикт не выводим |
| `if`/`then`/`else`, `dependentSchemas`, `dependentRequired` | не поддерживаем; запись в отчёт анализа (`UnsupportedOpenAPIError`/issue). Основание — §1: ноль вхождений |
| бизнес-неуспех внутри 2xx (Slack) | **не выводится из спеки**: Slack кладёт свой 200-неуспех под `default`. Нужен либо хинт (`x-eazy-error: true` на ответе), либо ручная правка после генерации. Отчёт анализа обязан это назвать |
| где внутри конверта нагрузка | в спеке этого нет вообще: хинт `x-eazy-payload` на свойстве либо правило генератора «единственное поле-объект рядом с тегом», по умолчанию — ничего не проецируем |

Сегодняшнее состояние плагина для сравнения: `_flat_body_fields` отказывается работать при
`oneOf`/`anyOf`/`allOf`/`discriminator` (`ir.py:1577`), `_schema_type` разворачивает союз в
`A | B` (`ir.py:1795`), `const` не читается нигде. То есть весь §6 — новая работа, но она
механическая и не требует ни одного нового понятия в рантайме, кроме двух маркеров.

## 7. Матрица бэкендов (измерено, не предположено)

### 7.1. Что бэкенд проверяет сам

| Бэкенд | нет обязательного поля | неверный тип | лишнее поле |
|---|---|---|---|
| dataclass | ошибка | **принимает** | принимает |
| Pydantic | ошибка | **принимает** (`"yes"` → `True`) | принимает |
| msgspec | ошибка | ошибка | принимает |
| TypedDict | ошибка | **принимает** | **ошибка** |

Отсюда важный вывод: **«разбор сам всё разрулит» — не контракт.** Различение «по форме» (какая
модель загрузилась) работает по-разному на четырёх бэкендах и в двух из них ловит лишнее/неверное
прямо противоположным образом. Явный тег — единственная переносимая формулировка.

### 7.2. `Literal` против `Annotated`-маркера

| Написание | dataclass | Pydantic | msgspec | TypedDict |
|---|---|---|---|---|
| `Literal["customer"]` | **не поддерживается адаптером** | работает и валидирует | работает и валидирует | **не поддерживается адаптером** |
| `Literal[True]` | не поддерживается | работает | **невозможно** (msgspec: Literal только None/int/str) | не поддерживается |
| `Annotated[bool, Const(True)]` | грузится | грузится | грузится | грузится |

`UnsupportedModelTypeError: no model adapter supports _LiteralGenericAlias` — это наш собственный
пробел в адаптерах dataclass/TypedDict, его стоит закрыть отдельно от этой темы. Но даже после
починки `Literal[True]` на msgspec не появится, а булев тег — самый частый в мире (§1.2). Поэтому
переносимая форма — маркер, а `Literal` читается как его синоним (R6).

### 7.3. Tagged union

`MsgTagA | MsgTagB` (msgspec `tag="a"`, `tag_field="kind"`) грузится через `ModelAdapterRegistry`
правильно и на неизвестном теге даёт `ModelAdapterError`. Значит `oneOf` + `discriminator`
закрывается моделью и не требует от нас ничего.

## 8. Чего сознательно не делаем

- **`if`/`then`/`else`, `dependentSchemas`, `dependentRequired`.** Ноль вхождений в замерах.
  Разрешимый кусок этих конструкций (`if: {properties: {x: {const: V}}, required: [x]}`) и так
  выражается тегом; неразрешимый — это валидация, ей место в модели, а не в выборе кейса.
- **DSL над разобранной моделью** (`field("success").is_(True)`). D8 фазы 53 остаётся в силе:
  строковый путь не типизирован. Разница предложения в том, что оно вообще не язык выражений — это
  константа рядом с полем, которую проверяет mypy.
- **`discriminator` как наш собственный механизм.** Это модель (§7.3), а не кейс.
- **Вывод вердикта из спеки для 200-конвертов.** Спека Slack его не содержит; угадывать нельзя.

## 9. Дефект, найденный попутно

`fallback=` не участвует, если критерий отверг всех кандидатов, отобранных по статусу.
`Responses.inspect` выбирает `fallback` **до разбора** (`cases.py:719`: `if not candidates and
self.fallback is not None`), поэтому success-кейс на 200 остаётся кандидатом, после разбора его
`accept`/`succeeds` говорит «нет», `matches` пуст — и вызов заканчивается
`UnexpectedResponseError`, а не объявленной ошибкой fallback.

Проверено (`experiments/openapi_conditions/probe_fallback.py`, msgspec, 200 `{"ok": false, …}`):

```
fallback=Error(DEFAULT, Json(Failure))   ->  UnexpectedOutcome(attempted_models=('Ok',))
errors=(Error(DEFAULT, Json(Failure)),)  ->  ErrorOutcome(error=Failure(ok=False, error='x'))
```

Это ровно форма Slack (ошибка под `default`, статус 200) — то есть первый же сгенерированный SDK
на неё наступит. Чинится тем, что fallback рассматривается второй раз, после разбора, если
`matches` пуст. Место — фаза 53.5, независимо от судьбы этого предложения.

## 10. Решения к принятию

- **D1. Форма тега.** `Annotated[bool, Const(True)]` (предлагается) против класс-атрибута
  `__tags__ = {"success": True}` (короче, но имя поля строкой и mypy молчит) против «только
  `Literal`, а адаптеры починить» (невозможно для булевых тегов на msgspec, §7.2).
  Имя: `Const` (слово JSON Schema) или `Tag` (слово OpenAPI-дискриминатора).
- **D2. Судьба `Envelope`.** Удалить целиком (предлагается: не был в релизах, покрывается полностью,
  снимает асимметрию `succeeds`/`accept`) — против оставить как escape hatch для вычисляемых условий
  на уровне сервиса.
- **D3. `Payload[T]` против `unwrap=`.** `unwrap` — JSON-указатель до разбора, `Payload` — поле
  модели после. Оба нужны? Предлагается оставить оба и документировать: `unwrap`, когда в конверте
  нет ничего нужного, `Payload`, когда конверт ещё и решает исход.
- **D4. Момент.** Фаза 53.5 (документация + переписывание kad) сейчас в работе, диагностики
  D-53-04/05 уже написаны в рабочем дереве. Если D1/D2 принимаются, документацию про `Envelope`
  писать не нужно — дешевле сложить изменение в 53.5, чем выпустить и переписать. Альтернатива:
  закрыть 53 как есть и завести фазу 54.
- **D5. Кодоген (§6).** Отдельная фаза после 53: теги из `const`/`enum`, tagged union из
  `discriminator`, отчёт анализа на неразрешимые союзы и на `if/then/else`, хинты `x-eazy-*`.
