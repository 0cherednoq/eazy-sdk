# Фаза 56. Перестройка документации

Статус: `active`. Решения владельца приняты 2026-10-07, следующий шаг - 56.0.1.

Дата плана: 2026-10-07.

Основной читатель: исполнитель, который переписывает `docs-site/` и может начать с любого
места, прочитав таблицу «Состояние» в разделе 8.

Рабочие файлы фазы:

- этот план и его таблица «Состояние»;
- [56-pages.md](56-pages.md) - очередь страниц, 87 существующих и 31 новая;
- запись «Phase 56» в [STATUS.md](STATUS.md).

## 0. Результат фазы

Сайт документации получает четыре верхние вкладки вместо девяти плоских групп, один сквозной
пример вместо четырёх разрозненных и единый язык. Сквозной пример - SDK почты `mail.example`,
и каждая его тема показана дважды: через HTTP и через браузер, на одном и том же учебном
сайте.

Код ядра и плагинов фаза не меняет. Если пример нельзя написать чисто из-за пробела в API,
пробел записывается в долг ядра, а страница показывает то, что работает сегодня.

Фаза закрыта, когда выполнено всё из списка:

1. каждая страница входит в оглавление, строгая сборка Sphinx проходит без предупреждений;
2. в блоках кода на страницах нет `assert`, подменных транспортов и серверов-заглушек;
3. каждый показанный фрагмент взят из файла в `examples/`, который запускается в тестах, а
   вывод на странице совпадает с выводом файла;
4. обе линии сквозного примера, HTTP и браузерная, проходят целиком одной командой каждая;
5. в `docs-site/` и `examples/` нет настоящих доменов и названий сервисов, только `example`;
6. проза каждой страницы прошла `humanizer-ru`, линтер навыка даёт ноль ошибок;
7. в [56-pages.md](56-pages.md) нет пустых ячеек;
8. зелёные гейты из раздела 9.

## 4. Сквозной пример: SDK почты

### 4.1. Учебный сайт

Сервис называется «Почта» и живёт на `mail.example`. Форма API взята у настоящей почты, имя и
домен убраны. Слова ARMGS и адреса настоящих сайтов на страницах и в `examples/` не
встречаются, это проверяет гейт 56.2.5.

| Часть | Откуда форма | На учебном сайте |
|---|---|---|
| конверт `{status, body}` внутри HTTP 200 | настоящая почта | как есть |
| токен, зашитый в HTML страницы `/inbox/` | настоящая почта | как есть |
| `GET /api/v1/threads/status/smart` с `offset` и `limit` | настоящая почта | как есть |
| `GET /api/v1/user/short` | настоящая почта | как есть |
| проверка TLS-отпечатка клиента | настоящая почта | объясняет, зачем `curl_cffi` |
| форма входа в два клика, редирект на страницу второго фактора | настоящая почта | как есть, пути свои |
| композер письма: тост «отправлено», диалог «адрес отклонён», тишина | настоящая почта | как есть |
| отдельные ответы «аккаунт не найден» и «аккаунт заблокирован» | придумано | помечено как учебное |
| капча на шаге входа | придумано | помечено как учебное |
| подпись и шифрование отправки | придумано | помечено как учебное |
| пагинация курсором и готовой ссылкой | придумано | помечено как учебное |

Первая страница примера пишет прямо, что сервис учебный, а его форма снята с настоящего
почтового API.

Сайт один на обе линии. Он лежит в `examples/mail/site/` и состоит из чистой функции
«запрос в ответ» с общим состоянием аккаунтов. HTTP-линия получает его через хендлер,
браузерная через перехват запросов страницы. На страницы документации код сайта не попадает,
там только панели запроса и ответа и HTML-фрагменты.

Раскладка примеров:

```text
examples/mail/
  site/            учебный сайт: API, страницы, аккаунты
  http/            mail_sdk на HTTP, по файлу на главу
  browser/         mail_sdk на браузере, по файлу на главу
  __main__.py      python -m examples.mail http | browser
```

### 4.2. Главы и две линии

Каждая глава - одна страница с вкладками «HTTP» и «Браузер». Вкладки синхронны: выбор на одной
странице сохраняется на остальных. Таблица вариантов стоит над вкладками и общая для обеих
линий, потому что сайт отвечает одно и то же.

| № | Глава | HTTP | Браузер |
|---|---|---|---|
| 1 | Что строим | таблица ручек API | карта страниц сайта |
| 2 | Вход в три шага | три операции `identify`, `password`, `otp` | три операции страницы, каждая возвращает следующий шаг |
| 3 | Чем вход может закончиться | теги `Const` на моделях ответа и исключения | правила `Failure` и исходы |
| 4 | Капча на входе | `Guard` решает и повторяет шаг | виджет на странице, решатель, тот же шаг |
| 5 | Сессия и её обновление | `session_auth`, токен из HTML, обновление по сроку и по отказу | `BrowserLogin`, `BrowserSession`, один вход на контекст |
| 6 | Список писем | `Pages.offset`, `Pages.cursor`, `Pages.next_url` | коллекция `each(...)`, подгрузка по кнопке «ещё» |
| 7 | Отправка письма | `POST` с подписью HMAC | композер с тремя исходами |
| 8 | Шифрование тела | шифрование полей и всего тела | вкладки нет, см. ниже |
| 9 | Сборка SDK | корень с HTTP-роутерами | тот же корень с браузерными роутерами, сессия из браузера у HTTP-клиента |

Шесть случаев главы 3: неверный пароль, аккаунт не найден, аккаунт заблокирован, нужен второй
фактор, неверный код, нужна капча.

Асимметрия линий записана честно, а не закрыта выдуманным кодом:

- подпись и шифрование в браузере делает сама страница. В главах 7 и 8 браузерная вкладка
  говорит это одной фразой и показывает то, что у браузера на этом месте есть своего;
- в главе 7 это три исхода отправки. Письмо без подтверждения не повторяют: его ищут в
  «Отправленных» HTTP-запросом. Это настоящий приём настоящей почты и лучший довод за
  совместную работу двух линий;
- глава 9 сводит линии: браузер входит, HTTP-клиент с `curl_cffi` работает под той же сессией.

### 4.3. Что не так в черновике нейросети

Черновик из запроса проверен по коду плагина. Часть имён настоящая: `Failure` с асинхронной
фабрикой (`failures.py:48`), `inherit_errors=False` (`spec.py:72`), `CurrentDriver`
(`content.py:81`), порядок «помехи, отказы, исходы, дедлайн» совпадает с `outcomes.mdx`.

| В черновике | Что не так | Как делаем |
|---|---|---|
| один `act` вводит логин, жмёт, вводит пароль, жмёт | отказ после первого клика нельзя отличить от отказа после второго; капче между шагами негде появиться | три операции, по одной на шаг |
| второй фактор объявлен отказом `TwoFactorRequiredError` | для рассыльщика это верно, там нужен оператор. Для примера это шаг, а не тупик | исход `when(..., to=OtpStep)` |
| `_signed_in` с телом `_ = content` | заглушка ради сигнатуры | у `When` есть вторая форма, `to=` с классом состояния (`outcomes.py:59`); пробник 56.0.4 |
| `url.contains("reason=blocked")`, `reason=user_not_found` | таких адресов у настоящей почты нет | признаки учебного сайта |
| `sanitize_location(...)` | в `eazy_sdk_browser` такой функции нет | убрать или показать своей функцией в три строки |
| `acquire` из двух строк | скрывает, откуда берётся код второго фактора | в учётных данных лежит источник кода |
| один набор отказов на все шаги | правило шага пароля сработает на шаге логина | общие правила на роутере, свои у операции |

Форма, которую проверяет пробник. Каждый шаг возвращает следующий шаг типом:

```python
password_step = await entrance.identify(login=credentials.login)
after_password = await password_step.submit(password=credentials.password)
if isinstance(after_password, OtpStep):
    await after_password.confirm(code=await credentials.otp())
```

Последовательность шагов тогда проверяет тайпчекер. Это гипотеза: форма `to=` в документации
не показана, известно только её объявление. Если пробник её не подтвердит, глава пишется на
`then=`, а неудобство уходит в `plugins/browser/docs/CORE_DEBT.md`.

## 5. Правила страницы

1. **Код на странице берётся из файла.** Фрагмент вставляется директивой `literalinclude` по
   меткам из файла в `examples/`. Руками код на страницу не копируется.
2. **На странице нет обвязки.** Нет `assert`, `MockTransport`, `route.fulfill`, записывающих
   хендлеров, классов сервера. Страница показывает запрос и ответ панелями `http-exchange`,
   для браузера - HTML-фрагмент страницы.
3. **Фрагмент подписан файлом.** Первая строка блока несёт путь: `# mail_sdk/auth.py`.
4. **Импорты скрыты, но доступны.** Под фрагментом стоит раскрывающийся блок «Файл целиком» с
   полным запускаемым файлом.
5. **Вывод дан как вывод.** Отдельный блок `text` или комментарий под кодом. Тест сверяет его
   с настоящим выводом файла.
6. **После кода идёт разбор.** По абзацу на параметр или строку, которую читатель не угадает.
7. **Варианты ответа сведены в таблицу.** «Что ответил сайт, какое правило сработало, что
   получил вызывающий».
8. **Одна выноска на раздел.** Совет или предупреждение, не оба.
9. **Заголовок называет задачу.** «Вход по логину и паролю», а не «Login». Имя класса идёт в
   описание и первый абзац.
10. **Страница заканчивается ссылками «Дальше».** Две или три, без пересказа прочитанного.
11. **Домен только `example`.** `mail.example`, `api.mail.example`. Адреса почты в данных -
    `ada@mail.example`.
12. **Тема с двумя транспортами показана вкладками.** Вкладки «HTTP» и «Браузер» с общей
    группой синхронизации. Если у транспорта темы нет, вкладка говорит это одной фразой.

Правило 12 действует и вне сквозного примера. В руководстве оно касается страниц входа,
сессии, вариантов ответа и защиты.

## 6. Текст и humanizer-ru

Навык редактирует готовый текст и не пишет с нуля. Отсюда порядок работы над страницей.

1. Черновик: факты, код, таблицы. Новые страницы пишутся сразу по правилам раздела 5.
2. Аудит по `references/patterns.md`: таблица находок с цитатой и номером паттерна. Outline-тест
   для страниц от пяти абзацев.
3. Правка только по находкам.
4. Линтер навыка по прозе страницы через обёртку из шага 56.2.6.
5. Слепая проверка свежим агентом. Она обязательна для разделов «Начало работы» и «Разбор на
   примере», в остальных не нужна.

Особенности технического текста, которые навык сам не учтёт:

- идентификаторы API стоят в обратных кавычках и не переводятся;
- для остального действует словарь: операция, роутер, клиент, корень, сессия, исход, отказ,
  помеха. Английские вставки вроде «lifecycle input», «scoped SDK», «wire schema», «caller»
  заменяются русским словом или объяснением при первом появлении;
- справочник API сух по жанру. Там правятся только жёсткие запреты, голос не добавляется;
- 385 длинных тире снимаются правкой предложений, а не автозаменой на дефис.

Навык лежит в домашнем каталоге, а не в репозитории, поэтому его линтер остаётся локальным
шагом. В CI идёт собственная короткая проверка из шага 56.2.4.

`request/pipeline.py`, состояние попытки в `clients/attempts.py`, выбор кейса в
`response/cases.py`.

Адреса страниц меняются. Перенаправлений нет: версия альфа, а правила репозитория запрещают
слои совместимости.

## 8. Этапы и состояние

### 8.1. Как вести прогресс

1. Сессия начинается с таблицы «Состояние» ниже. Берётся первый шаг не в статусе `complete`.
2. Шаг закрыт, когда выполнено его условие из столбца «Готово, когда». В столбец
   «Доказательство» пишется команда и её результат, в столбец «Дата» - день закрытия.
3. Один шаг - один коммит с заголовком `Phase 56.N.M: ...`. План, очередь страниц и `STATUS.md`
   правятся в том же коммите. Каталог `docs/` в `.gitignore`, поэтому `git add -f`.
4. Страница закрыта, когда её строка в [56-pages.md](56-pages.md) заполнена. Строка правится в
   том же коммите, что и страница.
5. Отклонение от плана записывается в раздел 8.3 в момент, когда принято, с причиной.
6. Шаг, который нельзя закрыть, получает статус `blocked` и точную причину в доказательстве.
   Работа идёт дальше по шагам, которые от него не зависят.
7. Этап закрывается записью в `STATUS.md`: критерии выхода, команды, результаты.
8. Тест, который не запускался, не считается пройденным.

Статусы: `pending`, `active`, `blocked`, `complete`.

## 9. Гейты

```bash
uv run pytest -q
uv run mypy
uv run ruff check
uv run python scripts/docs_freshness.py check
uv run --group docs python docs-site/scripts/validate_docs.py
uv run --group docs sphinx-build -W --keep-going -b dirhtml -c docs-site docs-site/src/content/docs docs-site/_build/html
uv run python -m examples.mail http
uv run python -m examples.mail browser
```

Плюс проверки этапа 56.2 и локальный линтер навыка по каждой странице.

Известное ограничение машины: полный прогон `pytest` иногда не завершается из-за зависания
`socket.socketpair()`. Если повторится, в `STATUS.md` пишется точная причина, а прогон
повторяется.
