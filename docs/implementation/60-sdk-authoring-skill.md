# 60. Скилл «SDK по записи трафика»: техническое задание

Статус: реализация идёт в ветке `feat/sdk-capture-skill` с 2026-10-12. Что сделано и чем
реализация отличается от этого текста, записано в §12; ход работ — в `STATUS.md`, раздел
«Phase 60».

## 1. Цель

Скилл для Claude Code, который записывает работу пользователя с сайтом в браузере (трафик
и действия на одной шкале времени), по этой записи собирает декларативный SDK на Eazy SDK и
доказывает его работоспособность, проигрывая ту же запись без сети. Готовая запись со
стороны (HAR, выгрузка Burp) тоже принимается.

Скилл не заменяет кодогенератор `eazy-sdk-openapi`: там источник — спецификация, здесь —
наблюдения. Код пишет модель, а факты для неё и проверки результата дают скрипты. Модель не
читает сырую запись и не оценивает свой результат на глаз.

Вне рамок первой версии: браузерная линия (`eazy_sdk_browser`), WebSocket, обход защиты,
подбор подписи и шифрования запросов. Скилл обязан их распознать и назвать, но не решать.

## 2. Входные данные

| Вход | Обязателен | Откуда |
|---|---|---|
| Запись: каталог своей записи (§4.0) либо готовые файлы HAR / Burp XML | да | скилл записывает сам или берёт у пользователя |
| Стартовый адрес сайта, если записывает скилл | да | вопрос пользователю |
| Имя пакета и каталог результата | да | вопрос пользователю |
| Какие сценарии нужны (вход, чтение списка, …) | да | вопрос; по умолчанию всё, что есть в записи |
| Библиотека моделей (pydantic / dataclass / msgspec) | нет | по умолчанию pydantic |
| Транспорт (curl_cffi / httpx) | нет | по умолчанию curl_cffi с `impersonate` под браузер записи |
| Версия `eazy-sdk-core` | нет | установленная в целевом проекте |

Основной источник — собственная запись через браузер (§4.0): только в ней есть действия
пользователя и границы сценариев. Сторонние форматы первой версии: HAR 1.2 и Burp XML (с
base64 и без); они дают трафик без действий. Формат определяется по содержимому, а не по
имени файла: приёмочный файл называется `har`, а внутри Burp XML.

## 3. Этапы

Каждый этап оставляет артефакт в рабочем каталоге `.<пакет>-sdk-work/` целевого проекта и
имеет условие выхода. Следующий этап не начинается, пока условие не выполнено.

| № | Этап | Кто делает | Артефакт | Условие выхода |
|---|---|---|---|---|
| 0 | Приём | модель + вопросы | `intake.json` | названы пакет, сценарии, транспорт |
| 0а | Запись в браузере | пользователь, скрипт | каталог записи | браузер закрыт, запись цела; пропускается, если дана готовая запись |
| 1 | Нормализация записи | скрипт | `capture.json` | все записи разобраны, потери названы |
| 2 | Скрытие секретов | скрипт | `capture.redacted.json`, `secrets.json` | модель читает только скрытую копию |
| 3 | Опись | скрипт | `inventory.json`, `inventory.md` | каждая запись отнесена к операции или к шуму |
| 4 | План SDK | модель, утверждает пользователь | `sdk-plan.md` | пользователь утвердил |
| 5 | Генерация | модель по справочникам скилла | пакет SDK и тесты | пакет импортируется |
| 6 | Проверка | скрипт | `check-report.json` | все ворота из §7 зелёные |
| 7 | Отчёт | модель по отчёту проверки | `REPORT.md` | перечислено доказанное, предположенное и ненаблюдавшееся |

Этап 4 — единственная обязательная остановка на пользователя. На нём решается то, чего в
записи нет: какие параметры публичные, как назвать операции и ошибки, какие сценарии
оставить.

## 4. Скрипты

Скрипты этапов 1–3 работают на стандартной библиотеке и запускаются с `python -I`: запись —
недоверенные данные. Скрипт записи требует Pydoll и запускается через
`uv run --with pydoll-python`. Скрипты этапа 6 запускаются в окружении целевого проекта.

### 4.0 `capture_record.py`

Открывает браузер, пользователь сам заходит на сайт и делает всё, что ему нужно; скрипт
пишет трафик и действия в каталог. Скилл запускает скрипт в фоне, объясняет пользователю,
что делать, и ждёт завершения.

```
capture_record.py --url https://site/ --out captures/ [--chrome PATH]
                  [--profile DIR] [--proxy URL] [--screenshots] [--no-overlay]
```

**Драйвер — Pydoll.** Он ведёт обычный установленный Chrome напрямую по CDP, без
WebDriver, и сайт с защитой пускает пользователя так же, как в его собственном браузере.
Для записи это главное: на сайте, который не пустил, записывать нечего.

Что запись включает в браузере сверх самого Pydoll:

- области отладчика `Network`, `Page` и `Runtime`;
- скрипт-слушатель в изолированном мире каждой страницы и привязку CDP, существующую только
  в этом мире: собственным скриптам страницы не видны ни слушатель, ни привязка;
- панель меток — обычный элемент страницы, сайт может его увидеть.

`--no-overlay` убирает панель. `--no-actions` убирает скрипт, привязку и область `Runtime`:
остаётся один трафик.

**Запуск и остановка**

- видимое окно, по умолчанию чистый временный профиль: вход должен попасть в запись целиком.
  `--profile` — постоянный профиль, когда нужна уже живая сессия;
- запись кончается, когда пользователь закрыл браузер или нажал Enter в терминале;
- всё пишется на диск по мере поступления: падение браузера или скрипта не теряет записанное;
- service worker отключён, иначе часть запросов не видна;
- пишутся все вкладки и всплывающие окна контекста.

**Каталог записи** `captures/<хост>-<дата-время>/`

```
meta.json            браузер и версия, User-Agent, размер окна, язык, стартовый адрес,
                     время начала, версия скрипта
timeline.jsonl       одно событие на строку, общие часы и сквозной номер
exchanges/0001.json  запрос и ответ: метод, адрес, заголовки парами, статус, времена
bodies/0001.req.bin  тела байтами, после снятия Content-Encoding
bodies/0001.resp.bin
storage/             cookie в начале и в конце, localStorage и sessionStorage по origin
screenshots/         по меткам и переходам, только с --screenshots
secrets.local.json   введённые пользователем значения (см. ниже)
```

**События шкалы времени**

| Вид | Что записано |
|---|---|
| `navigation` | вкладка, адрес, причина: ввод адреса, ссылка, скрипт, переход сервера |
| `action` | `click`, `input`, `change`, `submit`, `keydown` (Enter, Escape), `upload`; элемент: роль, подпись, `name`, `id`, устойчивый селектор; вкладка и адрес страницы |
| `request` / `response` | номер обмена, тип ресурса, инициатор (скрипт, разбор страницы, пользователь), вкладка и фрейм |
| `request_failed` | номер обмена и причина |
| `cookie` | имя, домен и кто поставил: ответ (номер обмена) или скрипт страницы |
| `websocket` | открытие, закрытие, размеры кадров; содержимое — только как сигнал «вне рамок» |
| `mark` | метка пользователя |

**Метки сценариев.** Пользователь делит запись на сценарии: кнопка в плавающей панели
скрипта на странице либо строка в терминале (`вход`, `список писем`, `открыл письмо`). Метка
открывает сценарий, следующая его закрывает. Из меток получаются имена операций и
`scenarios.toml`. Запись без меток допустима: сценарии тогда делятся по переходам, а имена
утверждаются на этапе 4.

**Связь действия и запроса.** Каждому запросу скрипт приписывает последнее действие той же
вкладки и инициатора от браузера. Опись по этому отделяет запросы, вызванные пользователем,
от фонового опроса и аналитики, а в плане операция читается как «клик „Войти“ → `POST
/cgi-bin/auth`».

**Ввод пользователя.** Значение поля ввода в `timeline.jsonl` не пишется: там метка и длина.
Само значение уходит в `secrets.local.json` с пометкой поля (`type=password`, `name`,
подпись). Это даёт описи точное происхождение «ввёл пользователь» для логина, пароля, кода
второго фактора и поисковой строки. По одному трафику оно только угадывается.

**Требования к точности**

- заголовки запроса берутся такими, какими ушли в сеть, вместе с `Cookie`; повторы
  `Set-Cookie` сохраняются по одному;
- тело ответа читается по завершении запроса; ответ без тела (204, 304, переход) — не
  ошибка, а «провал запроса» после полученного статуса пишется как обмен со статусом;
- тела медиа и шрифтов больше порога не сохраняются: размер и хеш;
- запись ничего не фильтрует по хостам: шум отсекает опись, где решение видно и обратимо.

**Чего запись не даёт.** Порядок заголовков HTTP/2 и отпечаток TLS не записываются; их
воспроизводит `impersonate` у curl_cffi. В отчёте это названо непроверенным.

**Безопасность.** Каталог записи содержит пароль, cookie и токены живой сессии. Скрипт
дописывает `captures/` в `.gitignore` до первого записанного байта и печатает
предупреждение при завершении. Модель каталог не читает: только скрытую копию после §4.2.

### 4.1 `capture_normalize.py`

Приводит запись к одному формату. Вход — каталог своей записи (§4.0), HAR или Burp XML; у
сторонних форматов шкала времени состоит из одних обменов. Выход: шкала времени и список обменов с полями `method`, `url`, заголовки запроса
и ответа списком пар (повторы `Set-Cookie` сохраняются), тела байтами в base64, `status`,
порядковый номер и время.

Требования:

- определить формат по содержимому;
- снять `Content-Encoding` и транспортное кодирование, запомнив исходные значения;
- отделять заголовки от тела по пустой строке при любом переводе строк: XML-парсер сводит
  CRLF к LF, и разделитель `\r\n\r\n` в выгрузке Burp без base64 не находится;
- найти запись с потерями и сказать об этом явно. Признак: ответ объявлен `charset=UTF-8`,
  а в теле нет ни одного байта старше 127 при `lang` не из латиницы, либо размер тела
  расходится с `responselength`. Такая запись пригодна для описи, но не для проверки;
- склеить несколько файлов в одну ленту по времени.

### 4.2 `capture_redact.py`

Заменяет секреты стабильными метками вида `«secret:password:1»` и пишет соответствие в
`secrets.json`, который модель не открывает.

- под замену идут: пароли и одноразовые коды в формах, значения cookie и `Set-Cookie`,
  токены в query, заголовках, `Location` и телах, адреса почты и логины;
- одно и то же значение получает одну и ту же метку во всей ленте, включая вхождения внутри
  HTML и JSON: на этом держится трассировка значений в описи;
- значения из `secrets.local.json` своей записи скрываются первыми и сохраняют название
  поля, в которое их ввёл пользователь;
- `secrets.json` и `capture.json` попадают в `.gitignore` целевого проекта при создании.

### 4.3 `capture_inventory.py`

Собирает из скрытой записи факты, по которым модель пишет SDK. Ничего не выдумывает: что не
наблюдалось, то в описи отсутствует.

- **Сценарии**: отрезки шкалы времени между метками, для каждого — действия пользователя и
  вызванные ими обмены по порядку.
- **Хосты и роли**: какие хосты участвуют, куда ставятся cookie и с каким `Domain`.
- **Операции**: группировка обменов по `метод + хост + шаблон пути`; сегменты пути, которые
  меняются между образцами, становятся параметрами.
- **Параметры**: для query, полей формы, JSON-тела и заголовков — постоянное значение,
  меняющееся или производное. Отдельно: дубли одного значения под разными именами
  (`Login`/`username`), значения-метки времени, значения, которые сами являются JSON или
  query-строкой.
- **Происхождение значений**: для каждого значения запроса — где оно впервые появилось в
  ленте: `Set-Cookie`, параметр `Location`, фрагмент тела ответа (с контекстом для
  регулярного выражения или селектора), ввод пользователя (точно, по `secrets.local.json`,
  с названием поля) либо «вычислено скриптом страницы», когда значение не найдено нигде:
  это кандидат в подпись или отпечаток.
- **Переходы**: цепочки `3xx`, заглушки с `<meta http-equiv="refresh">`, набор cookie до и
  после каждого шага.
- **Варианты ответа** на операцию: `статус × медиа-тип × шаблон Location × значения полей
  конверта`. Два образца одной операции с разным исходом — кандидаты в `success`/`errors`.
- **Конверт**: общие верхние ключи JSON-ответов одного хоста (`{status, body}`).
- **Схемы**: выведенная схема JSON-ответа со слиянием по образцам; поле, встреченное не во
  всех элементах, помечается необязательным.
- **Пагинация**: пары `offset/limit`, `page/size`, курсор, ссылка на следующую страницу и
  поле итога в ответе.
- **Шум**: статика, аналитика, отчёты CSP, фоновый опрос без действия пользователя — с
  причиной исключения.
- **Сигналы вне рамок**: подпись, шифрованное тело, страницы защиты, WebSocket.

### 4.4 `sdk_scaffold.py`

Создаёт каркас пакета: `pyproject.toml` с зависимостью на установленную версию
`eazy-sdk-core` и нужными extras, раскладку каталогов из §5.1, `tests/conftest.py` с
загрузчиком записи, строки в `.gitignore`.

### 4.5 `sdk_replay.py`

Проигрывает сценарии записи через настоящий SDK без сети: транспорт заменён на
`eazy_sdk.testing.AsyncRecordingHandler`, который на запрос SDK отдаёт записанный ответ.
Сопоставление — по `метод + хост + путь` в порядке записи.

Сообщает по каждому сценарию:

- итог: значение или исключение с цепочкой причин;
- запросы SDK, которых нет в записи;
- записи, которые SDK не запросил;
- расхождение запроса SDK с записанным: имена query, имена и порядок полей формы, ключи
  JSON-тела, набор cookie и заголовки. Заголовки делятся на три группы: обязанные совпасть
  (`Origin`, `Referer`, `Content-Type`, `X-Requested-With` и собственные заголовки сайта),
  принадлежащие транспорту (`User-Agent`, `Accept-Encoding`, `sec-*`: их ставит
  `impersonate`) и прочие, которые попадают в отчёт как кандидаты в `inject`.

Сценарии и ожидаемые исходы описаны в `scenarios.toml`, который пишет модель на этапе 5 по
утверждённому плану.

### 4.6 `sdk_check.py`

Одна команда на все ворота из §7 с итоговым `check-report.json`. Код возврата 0 только при
всех зелёных.

### 4.7 `refs_freshness.py`

Сверяет справочники скилла с версией библиотеки: каждое имя из примеров импортируется из
установленного `eazy-sdk-core`. Запускается в CI библиотеки и первым шагом `sdk_check.py`.

## 5. Требования к создаваемому SDK

### 5.1 Раскладка

Образец — `armgs-sdk`: `hosts.py`, `config.py`, `security.py`, `exceptions.py`, `models/`,
`http/operations.py`, `http/routers.py`, `auth/steps.py`, `auth/service.py`, `examples/`,
`tests/`.

### 5.2 Правила

1. Операция — замороженный класс с `__http__`, опубликованный через `op()`. Декоратор
   `@api.get` не используется.
2. Каждый хост — предок роутеров; адрес привязывается через `bind(...)`. Адрес соседнего
   хоста в запросе — `service_url(Хост)`, а не строка.
3. В публичной сигнатуре только то, что знает вызывающий. Постоянные и служебные параметры
   уходят в `inject`. Спорные случаи решаются на этапе 4.
4. Cookie SDK не перечисляет: корень объявляет `Cookies(...)`.
5. Вход — обычные операции, сервис `AuthService` вызывает их по порядку и держит только
   ветвления. Сессия — модель с `Placed`-полями и `session_scheme`.
6. Исход, который сайт сообщает адресом перехода, — модель с `Location`. Исход в поле
   конверта — тег `Const` / `OneOf` / `Not`. Конверт объявляется один раз на предке роутеров.
7. Значение из HTML — модель документа с `Regex` / `CSS` / `XPath`; разбор функциями запрещён.
8. Пагинация — `__pages__`; генераторных методов в роутерах нет.
9. Переходы и заглушки с `meta refresh` выполняет клиент (`client_redirects`), а не цикл в SDK.
10. Импорт только из публичных модулей `eazy_sdk`. Приватные модули запрещены.
11. Ошибка — подкласс общего исключения SDK. Текст исключения не содержит адрес с query
    целиком: в нём лежат почта и токены.
12. Чего в записи не было, в коде нет. Предположение помечается в докстринге и попадает в
    отчёт; ненаблюдавшийся исход не получает собственного класса ошибки.

Запреты берутся из `armgs-sdk/docs/eazy-usage-audit.md` (двенадцать разобранных ошибок
первой версии) и раздела «Anti-patterns» `sdk-authoring-reference.md`.

### 5.3 Когда декларации не хватает

Скилл не обходит пробел библиотеки ручным кодом. Он записывает его в `LIBRARY-GAPS.md` с
минимальным примером и останавливает операцию с пометкой «заблокировано». Решение — за
владельцем библиотеки.

## 8. Приёмка на реальном случае

Приёмка идёт на двух записях одного сайта. Первая — имеющаяся

### 8.1 Что в имеющейся записи

### 8.2 Что должна показать опись

Пункты про происхождение `act_token`, `token` и `email` взяты из кода `armgs-sdk` и по
записи ещё не сверены: это первая проверка для `capture_inventory.py`. Остальное видно в
записи напрямую.

- три хоста и области cookie: `.armgs.team`, `.auth.armgs.team`, `.e.armgs.team`;
- `act_token` формы равен значению из страницы входа и cookie `act`;
- `Login`/`username` и `Password`/`password` — дубли одного значения;
- `page` формы и query страницы входа — адрес почты на третьем хосте;
- `Origin` и `Referer` формы указывают на хост `account`;
- у `POST cgi-bin/auth` два исхода на одном статусе 302, различаются `Location`;
- цепочка 4 → 5 → 6 → 7 как один переход клиента;
- `token` и `email` в query записи 8 взяты из тела записи 7;
- `_` — метка времени, `sort` и `filters` — JSON в query, `offset`/`limit` — пагинация;
- второй фактор, капча, блокировка и адресная книга в записи **не наблюдались**.

### 8.3 Критерии

1. Скилл на этой записи создаёт пакет с операциями входа и списком писем, ворота G1–G10
   зелёные.
2. Сценарий «неверный пароль» (записи 0–1) завершается исключением неверных учётных данных.
3. Сценарий «вход и список» (записи 2–8) возвращает страницу из 20 писем при итоге 71.
4. В созданном пакете нет операций второго фактора и отдельных ошибок капчи и блокировки;
   в отчёте они перечислены как ненаблюдавшиеся.
5. Пароль, cookie и токены из записи не встречаются нигде, кроме `capture.json` и
   `secrets.json`.
6. Новая запись сделана скриптом скилла: шкала времени содержит действия «ввод логина»,
   «ввод пароля», «клик входа» и связывает клик с `POST cgi-bin/auth`; пароль есть только в
   `secrets.local.json`; имена операций в плане взяты из меток.
7. На новой записи сверка заголовков показывает, чего `armgs-sdk` не шлёт по сравнению с
   браузером; каждое расхождение отнесено к транспорту, к `inject` или к отчёту.
8. Сравнение с эталоном: операции, параметры в `inject`, модели исходов и сессии совпадают
   с `armgs-sdk` по смыслу; каждое расхождение объяснено в отчёте.

### 8.4 Проба от 2026-10-12

Проверено, что проигрывание записи через настоящий SDK осуществимо уже на библиотеке
0.2.0a14. Скрипты: `experiments/sdk_skill_probe/` (`burp_detail.py`, `replay_probe.py`),
запуск из `armgs-sdk`:
`PYTHONPATH=. uv run --no-sync python <путь>/replay_probe.py var/har [fix-title]`.

| Сценарий | Результат |
|---|---|
| неверный пароль, записи 0–1 | `InvalidCredentials`, оба запроса сопоставлены |
| вход и список, записи 2–8, запись как есть | `MailboxNotOpened`: `MailPage.title` не найден |
| то же с восстановленным заголовком страницы | `ThreadsPage`, 20 писем, итог 71, все 7 записей использованы |

Выводы пробы, уже учтённые в ТЗ:

- **Запись с потерями.** Выгрузка Burp без base64 заменила каждый байт кириллицы точкой:
  в файле нет ни одного байта старше 127. Критерий `<title>Почта</title>` на такой записи
  не срабатывает. Отсюда требование §4.1 о распознавании потерь и справочник
  `capture-howto.md`. Для приёмки запись нужно переснять с base64.
- **Перевод строк.** Разделитель заголовков в такой выгрузке — `\n\n` (§4.1). С неверным
  разделителем тела приходят пустыми, а вход всё равно доходит до третьего шага, потому что
  токен формы берётся из cookie запасным источником. Ворота G6 и G7 ловят именно это.
- **Запросы совпали.** Имена query и заголовки, кроме `Connection`, совпали с записанными;
  лишних запросов SDK не сделал. Сравнение значений и порядка полей формы проба не делала.
- **Запись снята с SDK, а не с браузера.** Она подтверждает согласованность SDK с самим
  собой, но не с сайтом: заголовки браузера в ней отсутствуют. Для приёмки скилла как
  генератора нужна запись из браузера.
- **Утечка в тексте исключения.** `InvalidCredentials` несёт адрес перехода целиком, с
  почтой в query. Отсюда правило 11 в §5.2.

## 10. Открытые решения

1. **Где живёт скилл.** Предложение: `skills/eazy-sdk-from-capture/` в репозитории
   библиотеки, версия вместе с ней, установка как плагин Claude Code. Иначе справочники
   разойдутся с библиотекой.
2. **Проигрывание в библиотеке или в скилле** (§9, первая строка). Предложение: сначала в
   скилле, перенос в `eazy_sdk.testing` после приёмки.
3. **Тесты созданного SDK.** Предложение: тесты проигрывания читают `capture.json` из
   каталога вне git; в репозиторий SDK запись не попадает, в CI эти тесты пропускаются.
   Альтернатива — класть в репозиторий скрытую копию с синтетическими значениями.
4. **Запись для приёмки.** Снимается `capture_record.py`; нужен оператор с учётными
   данными, желательно со вторым фактором и одним прикладным отказом JSON-API.
5. **Режим дополнения.** Первая версия создаёт SDK с нуля. Дополнение существующего SDK по
   новой записи — отдельная задача после приёмки.

6. **Драйвер записи — решено: Pydoll** (владелец, 2026-10-12). Запись идёт только в
   Chromium-браузерах; Firefox и camoufox в первую версию не входят.
7. **Панель меток на странице.** Плавающая панель удобнее терминала, но это внедрённый в
   страницу элемент, и сайт может его заметить. Предложение: панель по умолчанию, ключ
   `--no-overlay` оставляет только метки из терминала.

### 12.2 Что выяснилось про запись через браузер

Проверено на Chrome 154 и Pydoll 3.0.0.

- **Опросом действия не собрать.** Первый вариант читал буфер изолированного мира командой
  `Runtime.evaluate` и не включал область `Runtime`. Он теряет клик, который уводит со
  страницы: пока идёт переход, Chrome ставит команды к странице в очередь и выполняет их уже
  в новом документе. Удержание перехода через `Fetch` не помогает по той же причине.
- **Привязка CDP доставляет действие в момент события**, поэтому клик перед переходом
  приходит до гибели страницы. Привязке нужна включённая область `Runtime`.
- **Виден ли сайту включённый `Runtime`.** Классическая проверка (геттеры на `Error.stack`,
  `name`, `message`, `toString`, прокси в `console.debug`) на Chrome 154 даёт одинаковые
  счётчики при выключенном и включённом `Runtime`: по ней страница разницы не видит. На
  старых сборках Chrome эта проверка различала. Другие способы обнаружения не проверялись.
- **Без области `Page` скрипт нового документа запускается только для переходов самого
  отладчика.** После клика по ссылке или отправки формы страница остаётся без слушателя.
  Запись включает `Page` всегда.
- **На сайте с защитой запись не проверялась**: это требует оператора. Проверка из §4.0
  остаётся открытой.
